# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Trakka is an ultra-lightweight Go backend (target: <20MB RAM at runtime) for shopping lists and to-do lists, exposed as a JSON REST API and served alongside static PWA assets. It is designed to run identically under Docker and Podman rootless, and is held to explicit security rules (parameterized SQL only, strict URL scheme validation, hardened HTTP response headers) — see the "Security rules" section below before touching handlers or the frontend.

## Commands

```bash
go build -o trakka ./cmd/server    # compile
go vet ./...                       # static checks
gofmt -l .                         # list any non-gofmt-formatted files (should be empty)
go mod tidy                        # sync go.mod/go.sum after dependency changes

# Run locally (no container needed — pure Go, no CGO)
PORT=8080 DB_PATH=./trakka.db STATIC_DIR=./static TEMPLATES_DIR=./templates go run ./cmd/server
```

There is no test suite yet (`go test ./...` has nothing to run). If you add tests, standard `go test ./...` applies; there's no custom test runner or build tag scheme.

### Container workflow

```bash
docker compose up -d --build              # Trakka only
docker compose --profile calendar up -d   # Trakka + Radicale (CalDAV sync)
podman-compose up -d                      # same compose.yml works unchanged
```

## Architecture

The backend is split into a thin entry point plus several internal packages, deliberately separated so persistence, HTTP concerns, auth logic, and shared types don't bleed into each other:

```
cmd/server/main.go     entry point: config, wiring, graceful shutdown, -healthcheck probe
internal/config/       env-var config loading
internal/models/       House/List/Item/User/Session/HouseMember structs shared by db and handlers
internal/db/           all database/sql usage lives here — nowhere else imports it
internal/auth/         non-HTTP auth logic: bcrypt, session tokens, hand-rolled OIDC client
internal/handlers/     routing, request validation, JSON responses, session middleware, /auth/... handlers
internal/validate/     small reusable input validators (currently: URL scheme)
internal/scraper/      best-effort background price lookup for an item's URL (OpenGraph/JSON-LD/microdata)
static/                PWA assets served at "/" (index.html, js/, locales/ (FR/EN dictionaries), sw.js, manifest.json, icons/)
templates/             login.html, rendered via html/template
```

`templates/login.html` (via `html/template`, `Content-Type: text/html`) is the one exception to "no server-side rendering" — it genuinely needs server-injected per-request data (whether OIDC is configured, login-vs-register mode, a canned error message), which nothing else in this app does. `internal/handlers.Routes()` still serves `static/` purely via `http.FileServer`; don't add further `html/template` rendering unless something else genuinely needs server-injected per-request data the same way.

- **`internal/handlers` never imports `database/sql`** — it only calls methods on `*db.DB` (e.g. `GetList`, `CreateItem`) and checks for the sentinel `db.ErrNotFound` to decide between a 404 and a 500. Keep that boundary: if a handler needs a new query, add a method to `internal/db`, don't reach around it.
- **Routing** uses the Go 1.22+ standard-library `http.ServeMux` method-pattern syntax (`mux.HandleFunc("GET /api/v1/lists", ...)`) in `internal/handlers/app.go` — there is no router dependency (no Gin, no chi). Unmatched methods on a registered path pattern get an automatic 405 from the stdlib mux; don't hand-roll that check in handlers.
- **Database**: `modernc.org/sqlite` (pure Go, no CGO) — this is load-bearing for the static-binary/no-CGO build in the Dockerfile. Do not swap in `mattn/go-sqlite3` or any CGO-based driver.
  - The DB connection pool is deliberately capped at `SetMaxOpenConns(1)` / `SetMaxIdleConns(1)` (see `Open()` in `internal/db/db.go`). SQLite only allows one writer at a time and modernc's driver gains nothing from pooling; this avoids `SQLITE_BUSY` errors under concurrent requests. Don't "fix" this by raising the pool size without understanding why it's there.
  - Schema lives in `internal/db/schema.sql`, embedded into the binary via `//go:embed` (which is why it must live inside the `internal/db` package directory, not at the repo root) and applied idempotently (`CREATE TABLE IF NOT EXISTS`) on every startup — this doubles as the migration mechanism. There is no separate migration tool/framework. To evolve the schema, add new idempotent `CREATE ... IF NOT EXISTS` statements rather than editing existing `CREATE TABLE` statements in place (existing deployed `/data/trakka.db` files won't be rewritten). See [docs/DATABASE.md](docs/DATABASE.md#evolving-the-schema) for the `ALTER TABLE` caveat.
- **Go version pinning is intentional and fragile**: `go.mod` currently declares `go 1.27.0` and pins `modernc.org/sqlite v1.57.0` (its own `go.mod` requires `go 1.25.0`, comfortably under 1.27.0), matching the `golang:1.27.0-alpine` build stage in the `Dockerfile`. These three numbers (go.mod's `go` directive, the sqlite driver version, and the Dockerfile's builder image tag) must move together. Running `go mod tidy` carelessly (e.g. `go get -u`) will pull a newer `modernc.org/sqlite` that bumps the required Go version past what the Dockerfile's builder image provides, silently breaking the Docker build stage without touching the Dockerfile. If you upgrade the driver, bump the Dockerfile's builder image in the same change (pin an exact `golang:<version>-alpine` tag — Docker Hub publishes one per patch release — rather than a floating minor-only tag, so the build doesn't depend on when that tag last moved) and verify `go.mod`'s `go` directive still matches.
- **Config is env-var only**, loaded once in `internal/config.Load()`: `PORT` (default `8080`), `DB_PATH` (default `/data/trakka.db`), `STATIC_DIR` (default `/app/static`), `TEMPLATES_DIR` (default `/app/templates`), `BASE_URL` (required only if OIDC is configured), `OIDC_ISSUER`/`OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET` (all-or-nothing — `Config.Validate()`, called from `main.go` right after `Load()`, errors out at startup if only some are set), `SESSION_COOKIE_SECURE` (default `true`), `SESSION_TTL_HOURS` (default `720`). No config file, no flags other than `-healthcheck`.
- **Healthcheck is in-process**: `trakka -healthcheck` (implemented in `cmd/server/main.go`) does an HTTP GET against its own `/healthz` and exits 0/1. This is what `Dockerfile`'s `HEALTHCHECK` and `compose.yml`'s `healthcheck.test` both call — it exists specifically so the runtime image doesn't need `curl`/`wget` installed. If you change the healthcheck behavior, update both call sites.
- **Graceful shutdown**: `cmd/server/main.go` selects on a signal channel and a server-error channel; on SIGINT/SIGTERM it calls `srv.Shutdown(ctx)` and only then returns from `main`, which runs the deferred `database.Close()`. Don't call `os.Exit()` on the shutdown path — it would skip that deferred close.
- **Logging** uses `log/slog` (structured JSON to stdout), not the plain `log` package. `internal/handlers.Recover` is a last-resort panic safety net, not a substitute for the explicit `if err != nil` handling used everywhere else — every predictable failure path already returns an error before it would reach that middleware.
- **API shape**: `/api/v1/houses` (groups lists; a list belongs to exactly one house via `house_id`; a house has one or more members via `house_members`), `/api/v1/houses/{id}/members` (roster + invite-by-email + remove), `/api/v1/lists` (filterable by `?house_id=`/`?type=`; a list `GET` by id embeds its `items`) and `/api/v1/items` (filterable by `?list_id=`, with `PATCH` supporting partial updates like toggling `done` without resending the whole item). Full endpoint reference: [docs/API.md](docs/API.md).
- **Recurring items**: an item can carry `recurrence_rule` (`TEXT`, nullable — one of `DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY` or the custom `EVERY_X_DAYS:<n>` form, validated by `internal/validate.Recurrence`), `due_date` (`TEXT`, `YYYY-MM-DD`, validated by `internal/validate.Date`), and `recurrence_end_date` (same format/validator). All three are `addColumnIfMissing`-guarded the same way as `price`/`target_month`. `items.is_recurring` (`INTEGER NOT NULL DEFAULT 0`) is never a separate input anywhere in the stack — `internal/db.CreateItem`/`UpdateItem` always write it as `recurrence_rule IS NOT NULL`, so the two columns can never disagree. The behavior that makes this "recurring" rather than just three inert columns lives in `internal/handlers.applyRecurrenceCompletion` (`internal/handlers/recurrence.go`), called from `handleItemsUpdate`/`handleItemsPatch` right before the final `db.UpdateItem`: when a recurring item's `done` transitions `false → true` (checked against the item's *previous* `Done`, the same pattern `previousURL` already uses for the image-invalidation logic), it computes the next occurrence's `due_date` via `nextDueDate` (advancing from the item's current `due_date`, or from today if it has none yet, by the rule) and flips `Done` back to `false` — the item is un-checked with an advanced date instead of staying marked done, and instead of cloning a new row per occurrence, so a recurring chore never accumulates one item per completion (the "décale simplement la date" alternative, chosen for exactly that reason). If `recurrence_end_date` is set and the computed next occurrence would land after it (a plain string comparison, since both are `YYYY-MM-DD` and stay lexicographically comparable), the item is left `done: true` instead and never advances again. Clearing `recurrence_rule` (empty string via `PATCH`, or omitting it via `PUT`) clears `due_date`/`recurrence_end_date` along with it, since neither means anything once an item stops recurring. The frontend's recurrence `<select>` (`static/js/list_view.js`, in both the create-item form and the edit-item modal, not gated by `data-shopping-only` since a recurring chore applies to `todo` lists just as naturally as a shopping item) only offers the four fixed cadences — `EVERY_X_DAYS:<n>` is API-only, accepted for forward compatibility but with no UI to set it yet. A recurring item's row shows a small 🔄 badge with the translated frequency (`recurrenceBadgeLabel`/`buildRecurrenceBadge`) that stays in place across completions. Because the PATCH that checks an item off can be queued offline, `static/sw.js` carries a hand-kept JS port of the same completion logic (`applyRecurrenceCompletionOffline`/`nextDueDateOffline`, called from `applyOptimisticEdit` and `resolveAgainstPendingCreate`) so a recurring item checked off while offline advances immediately in the local optimistic state instead of sitting "done" until the sync queue flushes and a refetch corrects it — **any change to the Go rule-handling must be mirrored there by hand**, since there's no code sharing between the two runtimes. Verified end-to-end in three real headless-Chromium (Playwright) sessions: create-with-recurrence via the item form and badge rendering, the edit-modal round-trip (open → empty prefill → set MONTHLY → save → badge appears → re-open shows MONTHLY prefilled → clear → badge gone), and — with `BrowserContext.setOffline(true)`, after confirming the service worker actually controlled the page first — checking a recurring item off while offline: it stayed in the active section with its badge (not moved to "done"), confirming `applyRecurrenceCompletionOffline` fired. No console errors in any of it.
- **Automatic price & image lookup**: when an item is created, or its `url` changes, `internal/handlers.scrapeProductInfo` (`internal/handlers/scrape.go`) kicks off a detached goroutine — never `r.Context()`, which is canceled the moment the response is written — that calls `internal/scraper.FetchProductInfo(ctx, url)` **once** and writes back whichever of `price`/`image_url` the item is still missing (an explicit `price` in the request only skips price detection — the image is still looked up) via `db.UpdateItemPriceIfMissing`/`db.UpdateItemImageIfMissing`. Both of those methods' `WHERE ... AND url = ? AND <column> IS NULL` guards are what makes this safe to run detached from the request: a slow scrape can never clobber a price/image the user already has, or one for a since-changed `url`, no matter how the race resolves. Unlike a purely fire-and-forget design, `handleItemsCreate`/`Update`/`Patch` (`internal/handlers/items.go`) each wait up to `syncScrapeTimeout` (2.5s) on that goroutine before responding: if it lands in time, the response already carries the real `price`/`image_url` and a response-only `price_status: "found"` field (`models.Item.PriceStatus`, `json:"price_status,omitempty"`, never persisted, never present on a plain `GET`); if not and a price was still needed, `scrapeProductInfo` returns `"pending"` and the goroutine keeps running in the background exactly as the original fully-async design always did — but if only the image was still outstanding (price was already known), it returns `"found"` instead, since price detection genuinely isn't pending; the image is treated as a best-effort enhancement that simply shows up next time the item is fetched if it's slow to arrive. `price_status` is `"none"` when there was nothing to scrape (no `url`, or no price found within the wait) — this is unaffected by whether an image was found. This bounded wait is what lets `static/js/list_view.js` update the DOM straight from the POST/PATCH response instead of reloading or polling — see the frontend bullet below — while still never blocking indefinitely on a slow or unresponsive site. `items.price_auto` (`INTEGER NOT NULL DEFAULT 0`, same 0/1-boolean convention as `done`) records whether the current `price` came from this lookup rather than a user — the frontend shows a small badge next to an auto-detected price, clickable to open the same edit-item modal used everywhere else; sending `price` in any request (including an explicit `null`) always resets it to `false`, since a manual value was supplied. `items.image_url` (`TEXT`, nullable) is scraper-only — there is no request field to set it manually — and is cleared back to `nil` whenever `url` changes to something new (both `PUT` and `PATCH` in `internal/handlers/items.go` compute this before calling `db.UpdateItem`), since an image found for the previous `url` no longer describes the item. `internal/scraper.FetchProductInfo` parses the page once (`extractProductInfo`) and looks for a price via OpenGraph/`product:` meta tags (`og:price:amount`), Schema.org JSON-LD (`price`/`priceAmount` inside an `Offer`), and classic microdata (`itemprop="price"`), and an image via OpenGraph (`og:image`), Schema.org JSON-LD (`image`, as a string, array, or nested `ImageObject`), and the Twitter Card tag (`twitter:image`) — each list in that same priority order — using `golang.org/x/net/html` to parse rather than regex-scraping raw HTML. A relative image URL is resolved to absolute against the page's own URL (`resolveImageURL`, `url.ResolveReference`) and only accepted if the result is `http`/`https` with a non-empty host — the same rule `internal/validate.URL` applies to `item.url` — so a `javascript:`/`data:` URI in `og:image` can never end up as an item's `image_url`. Because this makes the server fetch an arbitrary URL a user typed into the `url` field, its `http.Client`'s `Transport.DialContext` is replaced with an SSRF guard (`safeDialContext` in `internal/scraper/scraper.go`) that resolves the host itself and only ever dials a public IP (rejecting loopback/private/link-local/multicast, which also covers the `169.254.169.254` cloud metadata address) — dialing the checked IP literal directly, rather than letting the transport re-resolve the hostname, is what closes the DNS-rebinding TOCTOU gap a naive "check then dial" would leave open. Every failure mode (network error, timeout, blocked host, no recognizable price/image markup) is treated identically as "nothing found" — this feature must never fail item creation/update outright, and the bounded wait keeps it from blocking indefinitely either.
- **Authentication & authorization**: local email+password (bcrypt) and generic OIDC/OAuth2 SSO (Authelia/Authentik/Keycloak/Google, ...) both establish the same opaque, server-side session — an HTTP-only, `SameSite=Strict` cookie whose value hashes to a row in the `sessions` table (`internal/auth.Service`). Every `/api/v1/...` request is gated as a whole behind `(*handlers.Application).RequireSession` (wrapped once around a sub-`http.ServeMux` in `Routes()`, not per-route) — deliberately **not** a separate `internal/middleware` package, since that middleware needs `*db.DB` and `internal/handlers` needs to call it to build routes, which would be an import cycle either direction; it lives as an `*Application` method next to every other handler instead. `/auth/...` (login page, register/login/logout submit, OIDC redirect/callback) and all static assets stay unauthenticated by design — gating static files would break the service worker's cache-first app-shell strategy, so the auth boundary is the JSON API, and `static/js/app.js`'s `apiRequest()` handles the client-side redirect-to-login on a `401`. A house's lists/items are only visible to its members (`internal/handlers/rbac.go`'s `authorizeHouseAccess`/`authorizeHouseOwner`, checked against `house_members` via `internal/db`); `CreateHouseWithOwner` (the only way a house gets created through normal use) is the one place in `internal/db` that opens an explicit `sql.Tx`, so a house is never left without an owner. The OIDC client (`internal/auth/oidc.go`, `jwt.go`) is hand-rolled — discovery, Authorization Code + PKCE, JWKS fetch/cache, RS256 id_token signature verification — using only the standard library plus `golang.org/x/crypto/bcrypt` (the one new dependency this feature added), rather than pulling in `coreos/go-oidc`/`golang.org/x/oauth2`, per the "standard library wherever possible" convention below.
- **Docker build is multi-stage and CGO-free by requirement**: builder stage `golang:1.27.0-alpine` compiles `./cmd/server` with `CGO_ENABLED=0` to a static binary; runtime stage `alpine:latest` runs as a fixed non-root numeric UID:GID (`10001:10001`), chosen specifically so it maps cleanly under Podman's rootless user-namespace remapping — don't switch to a named `USER` without keeping the numeric UID pinned in the `Dockerfile`'s `adduser -u 10001`. The runtime stage `COPY`s both `static/` and `templates/` (the latter for `login.html`) alongside the binary.
- **`compose.yml`** must stay valid for both `docker compose` and `podman-compose` — avoid Compose fields that only one of the two supports. The `radicale` (CalDAV) service is optional and gated behind the `calendar` profile; it should never start by default.
- **PWA/offline (`static/sw.js`, `static/js/db.js`)**: full design in [docs/PWA.md](docs/PWA.md) — read it before touching either file. The short version: `db.js` is loaded both as a page `<script>` and via the service worker's `importScripts()`, so it must never reference `window`/`document`, only `indexedDB` and `self`. `sw.js` transparently intercepts every `fetch()` from `app.js`; offline mutations get a temporary `temp-list-*`/`temp-item-*` id and are queued in IndexedDB, and `remapTempId()` patches any still-queued request that depended on one once it gets a real server id. `app.js` also reads (never writes) `TrakkaDB.getQueue()` directly, purely to show the "N en attente" badge — the service worker remains the only writer of the queue/mirror stores; don't add a second writer. Houses get the same read-only mirror (`TrakkaDB.getHouses`/`putHouses`/etc.) but are deliberately **not** offline-writable — creating/renaming/deleting a house while offline returns a `503` rather than being queued, because queueing it would require a second level of temp-id chaining (list → house, on top of the existing item → list) that the offline design explicitly doesn't support; see "Houses are read-mirrored but not offline-writable" in [docs/PWA.md](docs/PWA.md). Session cookies are ambient/browser-managed, so a queued write replayed later by `flushQueue()` automatically carries whatever cookie is present at replay time — no header snapshotting needed — but `flushQueue()` special-cases a `401` reply (expired session) by leaving the entry queued instead of discarding it like an ordinary rejected `4xx`, so a session expiring mid-queue can't silently drop an offline edit; see "Session expiry vs. the offline queue" in [docs/PWA.md](docs/PWA.md). `/auth/...` requests bypass the service worker entirely (checked first in the `fetch` handler) — never cache-first-served, never offline-queued. **Service workers require a secure context** (`https://` or exactly `http://localhost`) — they silently don't register anywhere else, which is why `compose.yml` serving plain HTTP is only enough for `localhost` testing (see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)).

## Security rules

These are standing constraints for this codebase, not just how the current code happens to be written — preserve them in anything new:

- **SQL**: every query goes through `database/sql` parameter placeholders (`?`), exclusively inside `internal/db`. Never build a query string by concatenating or `fmt.Sprintf`-ing a user-supplied value into it.
- **URLs**: any user-supplied URL (currently: an item's `url` field) must pass `internal/validate.URL`, which requires an absolute `http://` or `https://` URL with a non-empty host — this blocks `javascript:`, `data:`, and similar schemes from ever being persisted. Apply the same validator to any future field that accepts a URL. The frontend (`static/js/app.js`) re-checks the scheme client-side before ever setting an `<a href>`, as defense in depth — keep that check if you touch the rendering code.
- **Response encoding**: JSON responses rely on `encoding/json`'s default `SetEscapeHTML(true)` behavior (escaping `<`, `>`, `&`) — never call `SetEscapeHTML(false)` on the encoder in `internal/handlers/json.go`.
- **Frontend DOM**: `static/js/app.js` builds all dynamic content with `textContent`/`createElement`, never `innerHTML` with interpolated data. Keep that pattern for any new UI code.
- **HTTP security headers**: `internal/handlers.SecurityHeaders` sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a `Content-Security-Policy`, and `Referrer-Policy: no-referrer` on every response, including static files. The CSP has two deliberate exceptions: `script-src` trusts `https://cdn.tailwindcss.com` (the Tailwind Play CDN script `static/index.html` and `templates/login.html` both load), and `style-src` allows `'unsafe-inline'` because that script generates utility CSS into a `<style>` tag at runtime rather than an external file — there was no way to use Play CDN without it; and `img-src` trusts any `http:`/`https:` source (not just `'self' data:'`) because an item's scraped product thumbnail (`items.image_url`, see the price & image lookup bullet above) can point at any storefront's CDN, with no fixed host list to name in advance — the same reasoning that already lets `item.url` link out anywhere, just extended to `<img src>` now that thumbnails render inline instead of only linking out. Everything else stays strict: no `'unsafe-eval'`, no other inline scripts, no other allowlisted hosts. If you add any other inline `<script>`/`<style>`, move it to an external file instead of widening this further. If Play CDN's ~400KB runtime cost ever needs to go away, switch to a precompiled Tailwind build (Tailwind CLI, output to `static/js/` or a new `static/css/`) instead of the CDN script — that would let `style-src` drop `'unsafe-inline'` again. The OIDC login flow is entirely server-mediated redirects (never a page-JS `fetch` to the IdP), so none of this needed loosening for OIDC support.
- **Passwords & sessions**: passwords are hashed with `golang.org/x/crypto/bcrypt` (`internal/auth.HashPassword`/`VerifyPassword`) — never store or log a plaintext password. Session tokens are `crypto/rand`-generated and stored **hashed** (`internal/auth.HashToken`, SHA-256) in the `sessions` table — the raw token exists only in the cookie and in-flight, so a database leak alone can't hand out live sessions. `Authenticate()` runs a dummy bcrypt comparison even on an unknown email/OIDC-only account, so failed-login timing doesn't reveal whether an email is registered.
- **CSRF**: the session cookie is `SameSite=Strict`, which is the app's CSRF defense for `/api/v1/...` — it's never attached to a cross-site request, form or `fetch`. `/auth/login`/`/auth/register` deliberately carry no separate CSRF token: there's no pre-existing session for a forged POST to hijack at that point, so a token there would add no real protection. Don't remove `SameSite=Strict` from the session cookie without adding an equivalent CSRF defense first.
- **OIDC id_token verification**: hand-rolled in `internal/auth/jwt.go`/`oidc.go` — hard-rejects any `alg` other than `RS256` *before* any key lookup (alg-confusion defense), verifies the RSA signature before ever trusting the claims, and checks `iss`/`aud`/`exp`/`iat` afterward. If you touch this code, preserve that ordering; don't reorder "check claims" before "verify signature".
- **SSRF (server-side request forgery)**: `internal/scraper.FetchPrice` is the one place this server makes an outbound HTTP request to a URL a user supplied (an item's `url` field) rather than one hard-coded at deploy time. It's the same category of risk as a Slack/Discord link-unfurler, and is defended the same way: `internal/scraper`'s `http.Client` uses a custom `Transport.DialContext` (`safeDialContext`) that resolves the target host itself and only ever connects to a public IP — rejecting loopback, private/ULA ranges, link-local (including the `169.254.169.254` cloud metadata address), multicast, and unspecified addresses — and dials that checked IP literal directly rather than letting the transport re-resolve the hostname, closing the DNS-rebinding TOCTOU gap a "resolve, check, then dial the hostname" approach would leave open. Any future feature that makes the server fetch a user-supplied URL must reuse this guard (or an equivalent one) rather than calling `http.Get`/`http.Client.Do` directly against untrusted input.

## Project conventions

Inventory of conventions established while building Trakka, to be followed for any future contribution.

### Backend (Go)

- Standard library only wherever possible: `net/http` (no third-party framework/router), `log/slog` for structured JSON logging, `database/sql` for data access, a hand-rolled OIDC/JWT client (`crypto/rsa`, `crypto/sha256`, `encoding/json`, `net/http`) rather than a third-party OIDC library. The only notable external dependencies are `modernc.org/sqlite`, `golang.org/x/crypto` (bcrypt only), and `golang.org/x/net/html` (used by `internal/scraper` to parse a fetched product page's HTML rather than regex-scraping it) — the two `golang.org/x/...` packages are quasi-stdlib, maintained by the Go team itself, so neither is really a step away from this convention.
- Strict package split (`cmd/server`, `internal/config`, `internal/models`, `internal/db`, `internal/auth`, `internal/handlers`, `internal/validate`) with a hard boundary: `internal/handlers` never imports `database/sql` and only knows about the methods exposed by `*db.DB` and the `db.ErrNotFound` sentinel. `internal/auth` holds non-HTTP auth logic (bcrypt, session tokens, the OIDC client) and is imported by `internal/handlers`, never the reverse.
- Routing via the `mux.HandleFunc("METHOD /path", ...)` syntax from the Go 1.22+ stdlib, never a third-party router (no Gin/chi/etc.).
- All SQL queries are parameterized (`?`), confined to `internal/db`, never built by concatenation/`fmt.Sprintf`.
- Schema versioned through idempotent statements (`CREATE TABLE/INDEX IF NOT EXISTS`) in `internal/db/schema.sql`, embedded via `//go:embed` — no separate migration framework; an existing `CREATE TABLE` is never edited in place.
- SQLite booleans stored as `0`/`1`, converted to Go `bool` in the `scan*` functions.
- Timestamps in UTC, ISO-8601 with milliseconds; IDs are positive `AUTOINCREMENT` integers.
- Config exclusively via environment variables, loaded once in `internal/config.Load()` — no config file, no CLI flags other than `-healthcheck`.
- Predictable errors handled explicitly (`if err != nil`) everywhere; the `Recover` middleware is a safety net for panics, not a normal error-handling mechanism.
- JSON responses go through centralized helpers (`decodeJSON`/`writeJSON`/`writeError`/`pathID` in `internal/handlers/json.go`) rather than per-handler duplicated code; unknown JSON fields in a request body are rejected (`400`), body capped at 1 MiB.
- `go build`, `go vet ./...`, and `gofmt -l .` must stay clean on every change; no third-party linter configured.

### Frontend (PWA, `static/`)

- Vanilla ES6+ JavaScript (`async`/`await`), **no dependencies, no build step, no framework**. Several classic `<script>` tags (`app.js`, `list_view.js`, `db.js`) share the same global scope instead of using ES modules — identifiers (`state`, `els`, `apiRequest`, etc.) are therefore shared implicitly across files.
- Every network call goes through the `apiRequest()` helper (never a raw `fetch` elsewhere), which centralizes error handling via an on-page error banner and redirects to `/auth/login` on a `401` (the single choke point that auth-gates the whole SPA). `/auth/...` endpoints (login, register, logout, OIDC) are classic form-`POST`s with full-page redirects instead, served from `templates/login.html` — not part of the `apiRequest()`/JSON world.
- DOM built exclusively via `document.createElement`/`textContent`, **never** `innerHTML` with interpolated data — defense in depth against XSS.
- Any URL rendered as an `<a href>` is re-validated client-side (`http(s)` scheme only) before use, mirroring the server-side validation (`internal/validate.URL`).
- CSS: Tailwind CSS via the "Play" CDN (`https://cdn.tailwindcss.com`), no local Tailwind build; supplemented by a minimum of custom CSS (`static/css/tokens.css` for design tokens, `static/css/base.css`).
- `db.js` never references `window`/`document` (only `indexedDB`/`self`) since it's loaded both as a page script and via the service worker's `importScripts()`.
- The service worker (`sw.js`) is the **sole writer** of the IndexedDB mirror and the offline write queue; `app.js`/`list_view.js` only read (`TrakkaDB.getQueue()`) to display a badge.
- Service worker caches are version-suffixed (`trakka-shell-v1`, etc.) — bump the suffix on every `APP_SHELL` change.
- **UI language: French by default, with an FR/EN toggle** — `static/js/i18n.js` (loaded before every other page script) detects `navigator.language` or a saved `localStorage['trakka:lang']` choice, fetches `static/locales/{fr,en}.json`, and applies it to any element flagged `data-i18n`/`data-i18n-placeholder`/`data-i18n-aria-label`; a discreet dropdown in the header (`#lang-button`/`#lang-menu`) lets the user switch and persists the choice. Static markup goes through those `data-i18n*` attributes; dynamic strings built in JS (`app.js`, `list_view.js`, `planning.js`) call `window.TrakkaI18n.t('some.key', vars)` (or the local `t()` wrapper in `app.js`) instead of hard-coding text — not every dynamic string has been converted yet (see "What's left" in the handoff section below), so grep for a literal French string before assuming it's already wired up. Code, comments, and documentation stay in English regardless of UI language.

### Docker / deployment

- Multi-stage build: `golang:X.Y.Z-alpine` (builder, `CGO_ENABLED=0`) → `alpine:latest` (runtime). The Dockerfile's Go version, `go.mod`'s `go` directive, and the `modernc.org/sqlite` version must stay in sync (see the Architecture section above).
- Non-root user with a **fixed numeric UID:GID** (`10001:10001`, via `adduser -u 10001` then `USER 10001:10001`), never a symbolic `USER` — needed for predictable behavior under Podman rootless.
- `compose.yml` must stay valid for both `docker compose` **and** `podman-compose` at once — avoid any Compose field not supported by both.
- Named volumes only (never bind mounts), to avoid UID permission issues under rootless.
- Optional services (e.g. `radicale`) gated behind a Compose profile (`calendar`), never started by default.
- `security_opt: no-new-privileges:true`, no privileged capabilities, no host networking.

### Documentation

- `CLAUDE.md` is the reference for cross-cutting rules and invariants (version pinning, security rules) — topic docs link back to it rather than duplicating the information.
- Docs explain the **why**, not just the what (e.g. why `ALTER TABLE` must be guarded manually, why a given bug was found by testing rather than by review).
- Code, comments, and technical documentation are in English; only end-user-visible strings (the UI) are in French.
